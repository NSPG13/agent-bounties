# Private posting draft rollout canary

Deploy `posting-draft-canary.html` and `posting-draft-canary.js` with the account
draft API before publishing the full posting interface. These new standalone
files load no existing journey, approval, login, wallet, or composer scripts.
The page never calls a funding, signing, legal, publication, or transaction API.

Open `https://agentbounties.app/posting-draft-canary.html` in an existing signed-in
browser. **Refresh account** reads the ordinary credentialed session endpoint
and displays only authentication, the opaque account HMAC ID, and the effective
draft-storage rollout flag. Normal account authentication remains mandatory.
Use the displayed ID for the existing `SITE_POSTING_DRAFTS_CANARY_ACCOUNT_ID`
deployment setting; the page itself cannot change settings. A disabled flag
prevents the test write. After enabling that account, refresh and run the check.

The expected protocol is:

| Check | Expected result |
| --- | --- |
| `GET /v1/site-auth/session` with credentials | HTTP 200, `authenticated:true`, a 64-character lowercase account ID, `posting_drafts_enabled:true` |
| New UUID `POST /v1/site-auth/posting-drafts/:id` | HTTP 200, revision 1; exact draft and locally computed canonical SHA-256 |
| Credentialed read of that UUID | HTTP 200, same draft, revision, and hash |
| Exact replay of the initial POST, including expected revision 0 | HTTP 200, same revision and hash |
| Changed canary goal with expected revision 0 | HTTP 409; subsequent read shows the unchanged original |
| Same UUID read with `credentials:omit` | HTTP 401 |
| Reload page and read the stored UUID under the same account | HTTP 200 with the same exact record; no POST |

All responses must have `Cache-Control: no-store`. POST relies on the browser's
normal Origin header and the server's existing explicit-origin check. No API
override, secret URL, authentication bypass, or alternate identity mechanism
is supported. HTTP success with an incorrect hash, revision, approval state,
recovery state, or draft fails the check.

The envelope is valid under the existing API but cannot be funded:

```json
{
  "schema": "agent-bounties/posting-draft-v1",
  "id": "fresh UUID generated by the page",
  "role": "post",
  "goal": "Private posting storage canary. No bounty requested.",
  "preferences": "Canary storage only.",
  "brief": null,
  "draft": null,
  "draft_stale": false
}
```

The save body uses `expected_revision:0`, `approved_draft_hash:null`, and
`recovery_state:{}`. There is no reward, address, verifier, accepted consent,
transaction, or fundable draft. The unsubmitted server record expires after
30 days under normal draft retention. The page writes only
`agent-bounties.private-draft-canary.v1` in sessionStorage, containing its own
operation ID and opaque account ID. It never enumerates or clears storage. A
lost response leaves that ID available for read-only recovery. Switching
accounts blocks resumption of the prior account's canary.

Record the visible pass results, exact release SHA, and reload result before
enabling the broader storage rollout. Passing this canary proves account draft
storage only. PostgreSQL ownership-isolation tests remain the gate for a
different authenticated account; an omitted-credentials request alone does not
prove that property. The full posting interface and canonical payment checks
remain separate rollout gates.

Run the isolated client checks with:

```bash
node --test scripts/test-posting-draft-canary.cjs
```
